# 草稿提交与人工审批

本轮交付范围是员工主动提交草稿、场馆授权管理员查看申请及变更差异、复核后通过或退回、保存审批记录。通过是审批状态，不是资源占档；本轮不新增资源占用、不修改原已批准排期，也不执行客户通知、支付或其他外部业务动作。制度和确定性规则仍使用明确初始化的虚构试点配置。

## 员工操作

1. 在 `/agent` 按原流程检索制度、查资源、校验，核对完整预览后确认创建草稿。
2. 打开 `/drafts` 的“我的草稿”，选择本人草稿，核对场馆、资源、起止时间、人数、用途及变更原因。
3. 点击“提交审核”。服务端重新检查本人业务权限、规则与方案，按当前草稿版本提交，并保存提交时快照和事件。
4. 在同一页面查看待审核、已通过或已退回状态，以及管理员意见和审批记录。

创建草稿的确认按钮不等于提交审核，模型的聊天文字也不能代替提交。原有草稿可在增量迁移后使用此流程，无需重新生成。已退回且内容仍适用时可按页面状态再次提交；需要更改内容时，返回Agent提供完整修正需求并新建草稿。当前没有原地编辑既有草稿内容的接口。

## 管理员操作

1. 使用管理员账号登录，打开 `/admin/approvals` 的“排期审批”。仅列出其有明确审核权的场馆中已提交和已处理申请。
2. 选择申请，查看申请人、候选方案、原排期和逐字段变更差异、提交与既往审核记录。
3. 核对实时复核结果：申请人是否仍有该场馆的业务和草稿权限，规则及制度是否适用，资源容量和已批准占用是否冲突，变更原版本与状态是否一致。
4. 复核可通过时点击“通过”；退回时填写具体原因。服务端在同一写事务中重新鉴权与校验，比较草稿版本和页面所见复核摘要，再保存决定及审计快照。
5. 发生409或页面提示资料变化时，刷新详情后重新核对，不自动重试旧决定。已处理的版本不能再通过另一条并发决定覆盖。

审核人不能审核自己提交的申请。管理员登录、普通场馆业务权限和场馆审核权是不同条件；技术管理员不会自动获得所有场馆或员工数据访问。员工只能读取本人草稿与记录，未提交的草稿不会出现在其他管理员审批列表。

## 图表与实际流程展示

管理员“排期审批”页顶部显示全部当前授权场馆内已提交申请的状态分布。待审核、已通过、已退回按当前申请份数统计，包含历史申请，不随下方状态筛选或趋势日期范围改变；点击状态数字可以筛选申请列表。未提交草稿、无当前审核授权的场馆不计入。统计由独立只读汇总接口完成，不从最近50份列表推算总量。

趋势可切换最近7天或30天，包含今天，日期按北京时间（UTC+08:00）计算，无记录日期补零。提交次数来自提交事件，处理次数来自通过与退回事件；同一申请的重复提交和再次处理会重复计次，因此不能把事件次数当作不同申请份数。悬停、点击或键盘聚焦数据点可查看当日数值，也可展开逐日数据表。读取失败时显示不可用和刷新入口，不用零代替失败。

手机端默认收起详细概览，只显示当前状态份数；助手默认收起五步明细，保留实际处理状态。点击“展开图表”或“展开步骤”可查看完整内容，显式展开/收起的选择会保存在本机浏览器。桌面默认展开，避免手机图表把申请列表或需求输入推到首屏之外。

员工草稿与管理员审批详情显示申请时段；变更另展示原排期基线和申请方案。一般采用共同刻度；相距较远导致条形难以辨认时，各行独立缩放并明确说明，完整日期、时长和资源编号始终保留。已提交申请的原排期仍是提交快照，其当前有效性以复核结果为准。

容量条表示申请人数相对当前资源容量，超限时同时显示文字和人数。冲突图展示申请与已批准占用的重叠部分；图中最多绘制3条，其他已返回时段保留在下方列表。它不是正式占档日历，已通过的申请不会被画成新增资源占用。

助手页的五步流程来自真实工具事件、持久执行日志、完整预览和员工确认。工具业务冲突或待人工核实时不会因HTTP成功而显示通过；未执行步骤保持未完成。刷新只读取已有记录，不重发创建或确认请求。页面提供关闭动效，系统减少动态偏好优先；切出页面或滚动离开流程区会暂停工作状态的循环动效。未加入模拟演示入口或演示按钮。

## 显式审核授权

业务授权保存在 `agent_business_grants`，本轮新增 `can_review_drafts`，旧授权默认值为0。管理员当前账号须有效、角色为admin，其对应场馆授权须启用且部门匹配管理员当前部门；审核权按场馆配置，允许该场馆审核人复核不同申请部门的已提交申请。

对已有对应场馆业务授权的管理员，先停止相同数据目录的服务，再从项目根目录执行：

```powershell
python scripts/manage_agent.py grant-review --username venue.admin --venue east
```

服务与CLI必须指向同一个 `CHAT_DATA_DIR`。此命令不自动给普通员工管理员角色，也不创建正式占档或代替员工提交。全新隔离演示环境可先按[安装与Agent初始化说明](../README.md)创建账号与显式虚构业务样本；已有业务授权被撤销时不能靠反复初始化恢复。

## 状态与记录

| 当前状态 | 允许操作 | 后续状态 |
| --- | --- | --- |
| `draft` | 本人主动提交，版本和当前业务校验满足 | `submitted` |
| `submitted` | 获该场馆审核授权的其他管理员通过 | `approved` |
| `submitted` | 获该场馆审核授权的其他管理员填写原因退回 | `returned` |
| `returned` | 本人在内容与当前条件仍有效时再次提交 | `submitted` |
| `approved` | 查看结果与审批记录 | 本轮不提供重新审批或占档动作 |

提交、通过与退回都会增加草稿版本，和事件记录原子保存。提交与决策均需 `expected_version`，通过另需详情返回的 `review_hash`；它绑定草稿内容和当前复核所依赖的资料，防止看过旧页面后对变化后的方案直接操作。冲突、权限或规则不满足时不能通过，仍可按页面要求填写原因退回。

审批事件保存操作者、动作、前后状态、草稿版本、意见、时间和相关内容/复核快照。事件不允许被应用更新或删除。记录保留在受保护的本地SQLite中，不发送给生成模型或外部追踪平台。

## HTTP接口

接口继续使用登录Cookie、同源与CSRF校验，以及统一 `code/message/request_id/data` 信封。所有编号均由服务端生成；客户端不得附带申请人、角色或通过状态来扩大权限。

| 方法 | 路径 | 请求或用途 |
| --- | --- | --- |
| GET | `/drafts` | 本人草稿页面 |
| GET | `/api/drafts` | 本人草稿列表；可按状态筛选 |
| GET | `/api/drafts/{draft_id}` | 本人草稿详情、原排期差异、复核和审批事件 |
| POST | `/api/drafts/{draft_id}/submit` | `{"expected_version":1}` |
| GET | `/admin/approvals` | 管理员审批工作台 |
| GET | `/admin/api/approvals` | 当前审核范围内的已提交/已处理申请 |
| GET | `/admin/api/approvals/summary?days=7` | 全量授权申请的当前状态份数与最近7/30天事件次数；仅管理员，`days`只接受7或30 |
| GET | `/admin/api/approvals/{draft_id}` | 审批详情及最新 `review_hash` |
| POST | `/admin/api/approvals/{draft_id}/decision` | `{"expected_version":2,"decision":"approve","comment":"核验通过","review_hash":"详情返回的摘要"}`；退回用 `decision="return"` 并填写非空意见 |

最终结果须读取接口的实际状态和记录，不能以HTTP 200、模型自述或按钮被点击替代确认。并发、陈旧版本和权限变化将返回相应错误，页面会提示刷新核对。

## 验证与当前边界

[审批契约测试](../tests/api/test_approvals.py)用隔离数据库与模型替身验证真实HTTP/JWT/CSRF、权限、草稿状态、差异、复核、竞争和审计，不对运行中的员工草稿作审批测试。[原Agent回归](../tests/api/test_agent.py)继续验证确认前零草稿、五轮预算和持久中断等边界。

后续正式业务还需单独确认审批岗位与级次、容量与缓冲规则、占档事务、新旧排期切换、通知、企业身份和日志留存要求。当前通过不会释放旧排期或抢占新资源，不能作为企业生产占档成功的依据。

本轮本地验证：66项离线回归通过，其中21项覆盖新增审批契约；隔离浏览器中完成员工提交、管理员通过及退回、员工查看结果与原因、变更差异展示。桌面及390px手机布局验证通过。全部审批验证使用合成账号和独立临时数据库，不表示实际员工草稿已被自动提交或批准。

图表扩展验证：既有66项与新增6项统计/事件契约共72个不同用例通过。隔离浏览器验证图表筛选与7/30天切换、数据表、时间轴/容量/冲突、实际步骤及刷新确认、权限失败、减少动态、统计错误清除与刷新恢复，以及手机默认收起和展开选择保存。wheel与源码包构建成功。
