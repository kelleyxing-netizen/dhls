# 管理后台第1批：账号与权限

版本：0.8.0；日期：2026年10月30日。

本批实现真实本地账号、员工/管理员角色、JWT Cookie鉴权、接口权限及登录/后台骨架。知识库上传、数据库提示词和对话审查按已确认的后续批次接入，当前页面会明确提示尚未启用。启动及账号命令见[README](../README.md#阶段2本机员工聊天)。

## 页面与接口

| 方法与路径 | 权限 | 当前行为 |
| --- | --- | --- |
| `GET /login` | 匿名 | Jinja2登录页；已登录时跳转工作入口 |
| `GET /` | 员工/管理员 | 原有聊天页；匿名跳转登录 |
| `GET /admin` | 管理员 | 跳转知识库入口 |
| `GET /admin/knowledge` | 管理员 | 知识库页面骨架 |
| `GET /admin/prompts` | 管理员 | 提示词页面骨架 |
| `GET /admin/conversations` | 管理员 | 对话审阅页面骨架 |
| `POST /auth/login` | 匿名，同源JSON | 校验账号密码、签发Cookie，返回公开身份和CSRF令牌 |
| `GET /auth/me` | 已登录 | 返回当前数据库身份及CSRF令牌 |
| `POST /auth/logout` | 已登录、CSRF | 撤销当前登录记录并删除Cookie |
| `GET /admin/api/status` | 管理员 | 当前角色、部门、场馆及`implemented_batch: 1` |
| `/config`、`/sessions`、`/sessions/{id}/messages`、`/chat` | 已登录 | 延续[员工问答接口](员工问答接口说明.md)，写请求须带CSRF |

员工直接访问任何已实现后台页面或后台API返回403；不会因为前端隐藏了菜单就省略后端授权。匿名后台页面跳转登录，API错误统一返回HTTP状态及`code/message/request_id/data`中文信封。

登录请求：

```json
{"username":"venue.employee","password":"由账号持有人设置的密码"}
```

账号为3至64位ASCII字母、数字或`_.@-`，以字母或数字开头，登录时去除两端空白并统一小写。开户密码为12至128字符，无默认值；登录输入不会修剪密码。拒绝额外字段，前端不能通过传`role`获得管理员身份。

登录或`GET /auth/me`成功后，`data`包含：

```json
{
  "id": "用户UUID",
  "display_name": "员工",
  "role": "employee",
  "department_id": "sales",
  "venue_id": "east",
  "csrf_token": "当前登录专属的随机操作令牌"
}
```

浏览器自动发送`auth_token` Cookie：`HttpOnly; SameSite=Strict; Path=/`，HTTPS环境加`Secure`。JWT不返回在JSON正文、不写localStorage。前端仅在内存或当前后台DOM中持有CSRF令牌，所有已登录写接口携带`X-CSRF-Token`，例如新建会话、提问和退出。可从`/auth/me`或`/config`恢复CSRF令牌；其值不是供应商密钥。

`POST /auth/login`仅接受`application/json`，拒绝跨来源登录。已登录写接口也检查`Origin`及`Sec-Fetch-Site`，拒绝跨来源请求；未开启跨域许可。后台HTML默认自动转义，聊天和错误文本通过`textContent`显示。`/config`中的`knowledge_is_demo`通过实际内容是否等于内置示例制度判断，不把已编辑的制度文件仅凭路径认作示例。

## 身份与数据边界

- 密码仅存Argon2哈希；JWT固定HS256，验证签名、签发者、受众、必需声明及有效期。
- JWT只标识用户和登录会话，不以令牌中的角色授权；每次请求联查数据库当前`role`、`is_active`和登录撤销状态。角色/部门/场馆变更在下一次请求生效，停用立即拒绝新的请求。
- JWT默认60分钟有效，无自动续期；退出后即使复制旧JWT也不能再次访问。重置密码或启停账号会撤销该账号全部登录。
- 请求已经开始生成的回答沿用请求开始的身份，本批不实现对进行中SSE的远程强制终止。聊天正文、最近6个完整问答对、引用、幂等和断线状态机制继续保留。
- 员工和管理员的普通聊天接口均只处理自己的会话；管理员角色不能在`/chat`指定员工会话进行代发。审计读取将由后续独立管理API实现。
- 当前每个账号仅有一个部门和一个场馆字段，当前单份制度由所有已登录账号共享，尚未实现文档ACL、多部门/多场馆授权集合或审计范围授权。本批不把这些身份字段表述为已完成制度隔离。
- 登录限流在单进程内按来源及账号限制一分钟内尝试次数，Argon2同时计算最多两个。生产多实例、持久限流、企业SSO及私有云部署仍需后续设计。

## SQLite增量迁移

`users`保留原有字段，追加：

| 字段 | 用途 |
| --- | --- |
| `role` | `employee`或`admin`，数据库CHECK约束 |
| `password_hash` | Argon2密码哈希；旧演示记录为NULL |

新增`auth_sessions`：`id`、`user_id`、`csrf_hash`、`created_at`、`expires_at`、`revoked_at`。JWT的`jti`对应该表主键，CSRF只以SHA-256摘要存库；登录成功时清理过期登录记录。时间戳使用UTC秒。

旧会话和消息不重建、不清空；没有密码的旧演示账号在迁移时停用，历史记录仍归原所有者。新账号使用新的UUID，不自动继承演示数据。账号CLI拒绝为旧演示账号重置/启用登录，需新建真实账号。

服务及账号CLI共享操作系统实例锁，账号命令须停服务后运行。修改`CHAT_DATA_DIR`时要确保账号初始化与服务指向同一目录。首次启动迁移前应备份已有SQLite及其伴随文件，运行目录中原始问题、回答和来源仍属于未脱敏本地数据。

## 密钥与本机运行

本机未配置`AUTH_JWT_SECRET`时，在忽略的运行目录中生成`jwt-signing.key`，后续重启复用；密钥损坏时拒绝启动，不自动替换。可以注入至少32字节独立随机密钥；签名密钥不能复用DeepSeek API密钥。

默认只监听loopback，单worker，不信任转发头。HTTPS部署须配置`AUTH_COOKIE_SECURE=1`、保护数据目录ACL和签名密钥，并另行设计受信反向代理；当前代码不等于已交付企业部署。Windows密钥文件继承数据目录权限，须由部署者限制服务目录访问。运行数据、密钥、缓存和依赖不提交仓库。
