# 阶段2员工问答接口说明

版本：0.8.0；日期：2026年10月30日。登录与管理员角色已接入，新增部分见[管理后台第1批说明](管理后台第1批说明.md)。

本阶段提供本机员工制度问答原型：FastAPI、SQLite、真实上游模型SSE及原生HTML/JavaScript页面。阶段1的500字切片、本地Embedding、FAISS、BM25和RRF检索继续复用，阶段1CLI仍可独立运行。启动命令见[根目录README](../README.md#阶段2本机员工聊天)。

## 运行与身份边界

默认运行地址为`http://127.0.0.1:8000`，仅限单worker。操作系统实例锁保护同一数据目录，第二个实例会拒绝启动；崩溃后锁由操作系统释放。不要用多个worker或多个实例共用当前SQLite目录。

页面和业务接口使用真实本地账号及JWT Cookie鉴权，员工和管理员均只能在普通聊天接口读写自己的会话。未登录页面跳转`/login`，API返回401中文JSON；写操作需要`X-CSRF-Token`。旧演示身份停用，`CHAT_DEMO_MODE`不再启用任何身份旁路。企业SSO和制度ACL尚未实现，当前单份制度由全部已登录账号共用。

Embedding在本地运行；生成模型从后端调用DeepSeek或兼容`chat/completions`的供应商。浏览器不接收供应商密钥。内置演示制度并非真实企业政策，来源编号校验也不等于回答事实准确或引用语义完全一致。本阶段不执行审批、占档、支付或其他外部业务操作。

运行期间使用启动时加载的制度和索引快照；修改制度后重启。数据库、模型、缓存、依赖、截图和临时QA目录均不提交仓库。

## 公共响应约定

JSON和每个SSE事件都使用相同信封：

```json
{
  "code": "OK",
  "message": "成功",
  "request_id": "服务端本次请求编号",
  "data": {}
}
```

`code`为稳定机器码，`message`为中文说明，`request_id`用于定位本次HTTP请求，也出现在`X-Request-ID`响应头。失败时`data.retryable`说明是否可稍后重试。`request_id`和客户端`Idempotency-Key`用途不同：后者应在同一问题重试时保持不变。

输入验证、身份、所有权、幂等冲突和配置检查在开流前失败时返回对应HTTP状态及JSON信封。开流后HTTP状态保持200，失败通过SSE的`error`事件表示，不能只凭HTTP 200判断问答成功。错误信息不包含原始上游响应、密钥或异常详情。

## 接口

| 方法与路径 | 输入 | 成功响应的`data` |
| --- | --- | --- |
| `GET /` | 登录Cookie | HTML聊天页面，非JSON |
| `GET /config` | 登录Cookie | `demo_mode: false`、`knowledge_is_demo`、`knowledge_ready`、`model_ready`、`history_rounds: 6`、`max_question_length: 2000`、公开`user`、`csrf_token` |
| `POST /sessions` | JSON对象，`title`可选，最长100字符 | HTTP 201；`id`、`session_id`、`title`、`created_at`、`updated_at` |
| `GET /sessions?limit=30` | `limit`为1至100，默认30 | `items`会话数组、`has_more`；按更新时间倒序，返回当前用户的会话 |
| `GET /sessions/{id}/messages?limit=50&before=20` | `id`为UUID；`limit`为1至100，默认50；可选`before`为正整数序号 | `items`、`has_more`、`next_before`；先取指定序号前最近一页，再以旧到新顺序返回 |
| `POST /chat` | 见下文 | HTTP 200、`text/event-stream` |

所有上述业务接口均要求登录；POST额外携带`X-CSRF-Token`。新建会话可提交`{}`；空标题使用默认值。会话列表的`has_more`表示当前`limit`截断，当前没有会话列表游标。消息分页的`next_before`可用作下一页的`before`；没有更早消息时为`null`。时间为UTC ISO 8601字符串。

`knowledge_ready`反映本次服务进程的制度索引是否就绪；`model_ready`只检查本地模型配置，不请求供应商验证密钥或连通性。

消息对象包含：

```json
{
  "id": "消息UUID",
  "turn_id": "本轮问答UUID",
  "role": "assistant",
  "content": "已保存的正文或残文",
  "status": "completed",
  "sources": [],
  "error_code": null,
  "error_message": null,
  "seq_no": 2,
  "created_at": "UTC时间",
  "updated_at": "UTC时间"
}
```

`role`为`user`或`assistant`。助手消息状态为`generating`、`completed`、`failed`或`interrupted`。用户问题会在接收时保存；只有其对应助手消息成功完整后，这一对才进入模型历史。

### POST /chat与SSE

请求必须带JSON和有效UUID形式的幂等键：

```http
POST /chat
Content-Type: application/json
Accept: text/event-stream
Idempotency-Key: 11111111-1111-4111-8111-111111111111
```

```json
{
  "session_id": "22222222-2222-4222-8222-222222222222",
  "question": "已批准的档期如何变更？"
}
```

示例UUID仅展示格式；`session_id`必须使用实际创建的会话。请求中的问题最长2000字符，去除首尾空白后不能为空；未定义的JSON字段会被拒绝，不接受客户端指定用户、部门、场馆或历史上下文。

前端用`fetch`发送POST并逐段读取`response.body`，采用流式UTF-8解码并按SSE空行分帧；原生`EventSource`不适用于这里的POST请求。正文分片边界任意，`delta.data.text`应按顺序拼接，不能假设一帧等于一个字。`: ping`为心跳注释，不是业务事件。

| 事件 | 信封内的`data` | 含义 |
| --- | --- | --- |
| `meta` | `session_id`、`turn_id`、`user_message_id`、`assistant_message_id`、`replayed` | 本次请求关联的持久化记录；首个业务事件 |
| `status` | `stage: retrieving`或`generating` | 检索或生成进度；重放可不发送 |
| `delta` | `text` | 真实上游正文片段；已完成结果重放时也可一次发送全文 |
| `sources` | `items` | 已校验并随回答保存的实际引用来源 |
| `done` | `status: completed` | 正文和来源已成功提交SQLite；成功终态 |
| `error` | `retryable`、`turn_id`、`partial` | 失败终态；信封顶层含错误`code`和中文`message` |

正常顺序为`meta → status* → delta* → sources → done`。失败时以`error`结束，`error`与`done`互斥，失败不会发送成功来源。网络断开时客户端可能收不到终态，应查询消息核对数据库状态；单独收到正文片段不代表成功。

`sources.items`从本次检索结果中提取回答实际引用的片段，每项含`source_id`、`chunk_id`、`filename`、`start_line`、`end_line`、`excerpt`和`document_version`。引用不存在的片段会失败；明确回答“未找到依据”且未引用片段时，成功结果可以没有来源项。原文及版本快照随回答保存，后续制度变更不会改写旧回答依据。

### 幂等、并发、断线与恢复

- 幂等键按当前用户保存，参数由会话和问题组成。同键同参已成功则重放原正文及来源；客户端应以`meta.replayed`识别重放，不要求分片边界一致。
- 同键同参仍生成时返回HTTP 409 `REQUEST_IN_PROGRESS`；同键异参返回409 `IDEMPOTENCY_CONFLICT`。不同键同时写同一会话返回409 `SESSION_BUSY`，SQLite局部唯一索引提供并发约束；其他会话可独立生成。
- 失败或中断后同键同参重试会复用原问答消息ID，避免重复插入用户问题。新问题使用新键，修改问题后也使用新键。
- 停止按钮通过中止`fetch`断开连接，后端取消上游并将未完成助手消息标为`interrupted`；已经提交成功的消息不会被中断覆盖。失败和中断残文可展示、可核对，但不进入后续6轮上下文。
- 启动恢复将崩溃遗留的生成中助手消息标记为`interrupted`，错误码为`STREAM_INTERRUPTED`，释放会话生成占用。已保存但客户端未收到`done`的回答，可用原幂等键重试恢复。

模型上下文只包含当前问题之前、同一会话最近6个成功完整问答对，按原顺序发送；当前问题另附本次top3检索证据。历史旧引用编号会移除，问题、历史和证据在发给生成模型前走演示脱敏流程。

## 错误码

开流前的主要HTTP错误如下，均使用中文JSON信封；未知路径和不支持的方法也遵循此格式。

| 错误码 | HTTP状态 | 说明 |
| --- | --- | --- |
| `INVALID_REQUEST` | 422 | 参数、UUID、问题长度、空白内容或幂等键无效 |
| `UNAUTHORIZED` | 401 | 未登录、JWT无效/过期/已撤销或账号不可用 |
| `CSRF_INVALID` | 403 | 写请求CSRF令牌或来源校验失败 |
| `SESSION_NOT_FOUND` | 404 | 会话不存在或不属于当前用户，二者不对外区分 |
| `REQUEST_IN_PROGRESS` | 409 | 同一请求仍在生成 |
| `IDEMPOTENCY_CONFLICT` | 409 | 同一请求编号被用于不同参数 |
| `SESSION_BUSY` | 409 | 当前会话已有其他生成任务 |
| `KNOWLEDGE_NOT_READY` | 503 | 制度索引未就绪 |
| `MODEL_NOT_CONFIGURED` | 503 | 生成模型配置缺失、格式不正确或未提供密钥 |
| `STORAGE_ERROR` | 500 | 消息保存或读取失败 |
| `NOT_FOUND` | 404 | 路径或资源不存在 |
| `METHOD_NOT_ALLOWED` | 405 | 请求方法不支持 |
| `HTTP_ERROR` | 对应HTTP状态 | 其他HTTP请求错误 |
| `INTERNAL_ERROR` | 500 | 未预期服务异常 |

开流后的`error`可能使用下列错误码；此时HTTP状态已经是200，必须读取终态。`STORAGE_ERROR`、`INTERNAL_ERROR`也可能发生在流内。

| 错误码 | 说明 |
| --- | --- |
| `RETRIEVAL_ERROR`、`RETRIEVAL_EMPTY` | 检索失败或没有可用证据 |
| `LLM_RATE_LIMITED`、`LLM_UPSTREAM_ERROR` | 模型限流、连接或供应商服务异常 |
| `LLM_PROTOCOL_ERROR` | 上游SSE、JSON或正文格式不兼容 |
| `LLM_INCOMPLETE` | 缺少完整结束标记、模型截断、非正常结束或正文过长 |
| `LLM_EMPTY` | 没有可用正文 |
| `LLM_TIMEOUT` | 上游等待或生成总超时 |
| `CITATION_INVALID` | 引用本次未提供的片段或没有必要的依据说明 |
| `STREAM_INTERRUPTED` | 本轮已中断，需核对记录或重试 |

上游正文开始后不会自动重新请求模型，避免拼接两个不同回答。上游正常结束须同时确认`finish_reason=stop`和`[DONE]`；只收到文字或连接关闭不能视为成功。
